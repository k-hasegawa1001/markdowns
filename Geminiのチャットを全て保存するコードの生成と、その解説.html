1. セキュリティポリシーによる通信遮断 (CSPエラー)

Refused to connect because it violates the document's Content Security Policy.

現代のセキュアなWebアプリケーションは、XSS（クロスサイトスクリプティング）などを防ぐために厳格なContent Security Policy (CSP) をHTTPヘッダで設定しています。お使いの拡張機能（Content Script）が、PDFを生成するために外部のAPIサーバー等へ fetch でチャットデータを送信しようとしましたが、サイト側のCSPで許可されていないドメインへの通信だったため、ブラウザが強制的にブロックしました。

2. 拡張機能のプロセス間通信の切断

Could not establish connection. Receiving end does not exist.

これは拡張機能の構造上よく発生するエラーです。ページに注入されたスクリプトが、バックグラウンドで待機しているService Workerに処理を依頼（chrome.runtime.sendMessage）したものの、長時間待機している間にService Workerがスリープしてしまったか、裏で拡張機能のプロセスがリロードされたことで、宛先を見失ってタイムアウトしました。

ご推察の通り、現在の画面では [data-message-author-role] がマッチして要素を取得しています。あの1行がどのように機能しているのか、詳しく解説します。

1. querySelectorAll の基本仕様

document.querySelectorAll() メソッドは、指定された CSS セレクターに一致する文書中の要素のリストを示す静的な（生きていない） NodeList を返します。 引数には、照合する 1 つまたは複数のセレクターを含めることができます。カンマ（,）で区切ることで、「A または B または C」というOR条件として機能します。

2. セレクタごとの解説

今回のコード querySelectorAll('user-query, message-content, [data-message-author-role]') は、以下の3つの条件のいずれかに一致する要素を探しています。

  • user-query: 先頭に .（ドット）がないため、クラスではなくHTMLタグ名を探しています。つまり <user-query> という独自のタグを探します。

  • message-content: これも同様に、<message-content> というカスタムタグを探します。

  • [data-message-author-role]: これがご指摘の箇所で、「属性セレクタ（Attribute selector）」と呼ばれるものです。特定の属性名を持つ要素を表します。タグの種類に関係なく、この属性が設定されてさえいれば取得対象になります。

3. なぜ存在しないタグまで指定したのか？

WebアプリケーションのHTML構造は、UIのアップデートに伴い頻繁に変更されます。実際に、以前のバージョンでは <user-query> などのカスタムタグが直接使われていました。

このように複数のセレクタを併記しておくことで、アプリ側で構造変更があっても、どれか1つがヒットすればスクリプトが壊れずに動作し続けるという防御的プログラミング（フェイルセーフ）のアプローチを取っています。

これには、ブラウザの仕様とAPIの制約が深く関わっています。具体的には以下の2つの理由があります。

1. URL.createObjectURL() が文字列を受け付けない

前回の解説で、a タグの href に設定するための専用のURL（blob:https://...）を発行する URL.createObjectURL() という関数が登場しました。

実は、この関数の引数は仕様として Blob オブジェクトか File オブジェクトしか受け付けません。 つまり、URL.createObjectURL("<html>...</html>") のように直接文字列を渡してURL化することはシステム上許可されていないのです。そのため、文字列を一旦Blobという「コンテナ」に入れる必要があります。

2. データに「型 (MIMEタイプ)」を持たせるため

単なる文字列は、プログラム上はただの文字の並び（String型）であり、「それが何のファイルなのか」というメタデータを持っていません。

Blobを生成する際に new Blob([htmlContent], { type: 'text/html' }) と指定することで、単なる文字の並びに「これはHTMLファイルである」という証明書（MIMEタイプ）を貼り付けることができます。これによって、ダウンロード時にブラウザやOSが正しいファイル形式として扱ってくれるようになります。

（補足）Blobを使わずに文字列のままダウンロードする方法もある？

実は、Blobを使わずに文字列をそのままダウンロードさせる「Data URIスキーム」という古いアプローチも存在します。

JavaScript 
// Blobを使わない書き方
const htmlContent = "<html>...</html>";
const encodedData = encodeURIComponent(htmlContent);
a.href = "data:text/html;charset=utf-8," + encodedData;

このように、文字列をURLエンコードして直接 href にねじ込む方法です。これならBlobインスタンスを作る必要はありません。

しかし、この方法には致命的な弱点があります。 ブラウザには「URLの文字数制限」が存在するため、今回のような「長大なチャット履歴」のHTMLをURLエンコードして埋め込むと、制限（数万文字程度）を超えてしまい、エラーになったり途切れたりしてしまいます。

一方、Blobを使った方法はメモリ上にファイルの実体を確保して、そこへの短いリンク（URL）を発行するだけなので、ギガバイト単位の巨大なデータであっても一瞬でダウンロード処理が可能です。

つまり、Blobのインスタンス化は「少し回りくどい手続き」に見えますが、大容量のデータを安全かつ確実にエクスポートするための「モダンなWebのベストプラクティス」だと言えます。
