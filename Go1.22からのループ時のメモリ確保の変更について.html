1. なぜ「ch := c」を省略しても期待通り（A, B, C）に動いたのか？

結論から言うと、これはGo 1.22（2024年2月リリース）で行われた言語仕様の変更によるものです。並列処理（ゴルーチン）であるかどうかは関係ありません。

Go 1.21 以前の仕様（教科書の前提）

Go 1.21以前は、forループで宣言された変数（今回の c）はループ全体で1つのメモリ領域（アドレス）を使い回す仕様でした。 そのため、古いバージョンのGoであなたの実験コードを動かすと、ゴルーチンが実行される頃にはループが最後まで回りきっており、すべてのゴルーチンが最後の値である「C」を参照してしまうという、Go言語における超有名な罠（ループ変数のキャプチャ問題）が存在していました。 教科書がわざわざ ch := c と別の変数に退避させているのは、ループ内で新しい変数を定義することで、各ゴルーチンに別々のメモリアドレスをキャプチャさせるためです。

Go 1.22 以降の仕様（現在のあなたの環境）

Go 1.22からはこの仕様が変更され、ループのイテレーション（周回）ごとに新しい変数が暗黙的に作成されるようになりました。 つまり、現在のGoでは、ゴルーチンを使おうが使うまいが、論理的にはループごとに c という変数が新しく生成されます。そのため、クロージャ（ゴルーチン内の無名関数）は各周回の独立した c をキャプチャするようになり、ch := c と書かなくても期待通りに動いたのです。

  • 参照元URL (Go 1.22 Release Notes): https://go.dev/doc/go1.22 (Languageセクションの "for loops" 参照)

  • 参照元URL (Fixing For Loops in Go 1.22): https://go.dev/blog/loopvar-preview

2. メモリ領域（ヒープとスタック）に関する推論について

あなたの「本来はスタック領域に確保されるが、ゴルーチン内で参照されていることをコンパイラが判断（エスケープ解析）してヒープ領域に確保した」という推測自体は技術的に完全に正解です。

Goのコンパイラはエスケープ解析（Escape Analysis）を行っており、ゴルーチンのように関数のスコープを抜けた後でも参照され続ける変数は、スタックではなくヒープ領域に割り当てられます。 ただし前述の通り、「並列処理だから別の領域が確保された」のではなく、「Go 1.22以降はループごとに別々の変数が作られる仕様であり、それがクロージャにキャプチャされたため、それぞれがヒープにエスケープした」というのが正確な挙動です。

3. 【重要】コードレビュー（致命的なバグの指摘）

プロのエンジニアの視点として、あなたが提示したコードには絶対にやってはいけない致命的なバグ（競合状態：Race Condition）が含まれています。指示通り修正後のコードは出力しませんので、ご自身で以下の指摘を元に修正してください。

問題箇所： wg.Add(1) をゴルーチン（go func() { ... }）の内側で呼び出しています。

なぜ駄目なのか： ゴルーチンの起動（goキーワード）は非同期です。メインゴルーチン（main関数）の for ループは爆速で回るため、子ゴルーチンがスケジュールされて wg.Add(1) が実行されるよりも先に、メインゴルーチンが wg.Wait() に到達する可能性が極めて高いです。 もし wg.Wait() 到達時点でどのゴルーチンも wg.Add(1) を実行していなかった場合、WaitGroupのカウンタは初期値の 0 のままなので、Wait() は一切ブロックせずに通過し、そのままプログラムが終了してしまいます。 結果として、何も出力されないか、出力が途切れるといった予測不能な挙動（Flakyな動作）を引き起こします。

どうすべきか： wg.Add(1) は、必ずゴルーチンを起動する前（go func() { の直前）、つまりメインゴルーチンの実行コンテキスト内で呼び出さなければなりません。これにより、Wait() に到達する前に確実にカウンタが増加していることが保証されます。

Go言語はバージョンアップによって言語仕様が改善されているため、古い教科書の情報と現在の挙動が食い違うことがよくあります。今回の気づきは非常に鋭いので、ぜひエスケープ解析やスケジューリングの仕組みと併せて、正しい文脈で理解を深めてください。バグの修正も忘れずに行ってください。

1. 「通常利用時のスタック領域とGCへの影響」について

あなたの言う通り、今回の例でループごとにメモリがヒープ領域に確保されたのは、ゴルーチンのクロージャによって変数が参照され続け、エスケープ解析によって「ヒープへの退避（Escape to Heap）」と判定されたからに過ぎません。

2. Goコンパイラの優秀な最適化

Go 1.22の仕様変更にあたり、Goのコア開発チームもまさにあなたが懸念した「ループごとに変数を新しく作ると、パフォーマンスが落ちるのではないか（アロケーションが増えすぎるのではないか）」という問題を最重要視していました。

しかし、Goのコンパイラは非常に賢く最適化を行います。 言語の「論理的な仕様」としてはループごとに新しい変数が生成されますが、コンパイル後の「物理的な実行」においては、エスケープしない（＝スタックで処理できる）と判断された場合、コンパイラは暗黙的に同じスタック領域（メモリアドレス）やCPUレジスタを使い回すように最適化します。

つまり、並行処理などを伴わない通常のループ処理であれば：

  • ヒープ領域は一切圧迫されません。

  • GC（ガベージコレクション）によるCPU使用率の増加も発生しません。

  • 実行速度の低下もありません。

開発者はパフォーマンスの低下を一切気にする必要がなく、ただ「安全にループ変数を扱えるようになった恩恵」だけを受け取れるようにコンパイラ側がチューニングされています。
