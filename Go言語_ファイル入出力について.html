Goの io.Reader インターフェースの仕様では、「データを一部読み込めた（n > 0）と同時に、ファイルの終端に達した（err == io.EOF）」という状態が返されることが許容されています。また、「データを一部読み込めた（n > 0）が、その途中でハードウェアエラーなどの致命的なエラーが発生した（err != nil）」というケースもあり得ます。

Go 
// ※概念的なイメージです
func (f *File) WriteString(s string) (n int, err error) {
    // 新しいメモリ領域を確保せず、元の string (s) が配置されている
    // メモリの先頭アドレスを、無理やり []byte のポインタとして読み替える

2. 実務的な最強のアプローチ：io.Copy

Go 
package main

import (
    "io"
    "os"
)

// 巨大なファイルをコピーする関数
func copyFile(srcName, dstName string) error {
    src, err := os.Open(srcName)
    if err != nil {
        return err
    }
    defer src.Close()

    dst, err := os.Create(dstName)
    if err != nil {
        return err
    }
    defer dst.Close()

    // 魔法はここで起こる
    _, err = io.Copy(dst, src)
    if err != nil {
        return err
    }

    return nil
}

このたった1行の io.Copy(dst, src) の背後には、ストリーム処理とOSの深いメカニズムを利用した2つの段階の最適化が隠されています。

1. なぜCSVに Fscanf を使ってはいけないのか？

CSVは一見すると「カンマで区切られた規則的なデータ」に見えますが、実務で扱うCSVには以下のような厄介な仕様（エッジケース）が必ず含まれます。

  • 値の中にスペースが含まれる場合： Fscanf はデフォルトでスペースや改行を「区切り文字」として認識してしまうため、意図せずパースがズレます。

  • 値の中にカンマが含まれる場合： CSVでは 123, "Apple, Inc.", 456 のように、カンマを含む値をダブルクォーテーションで囲む仕様があります。Fscanf にはこの「引用符で囲まれたカンマは無視する」という高度な仕様を解釈する能力がありません。

  • 空の列がある場合： 123,,456 のようにデータが欠損していると、フォーマット指定子（%sなど）と実際のデータ数が合わず、パースエラーを起こします。

【実務での正解】 Goには標準で強力な encoding/csv パッケージ が用意されています。CSVを扱う場合は、例外なくこれを使用します。これを使えば、上記のような複雑なエッジケースをすべて安全に自動処理してくれます。

2. なぜ実務で Fscanf は使われないのか？

最大の理由は「フォーマットの変更に対して脆すぎる（壊れやすい）から」です。

Fscanf(file, "%d %s", &v, &str) のように書いた場合、対象のファイルが「絶対に100%この形式から逸脱しない」という保証がなければいけません。しかし、実運用されるログファイルやデータは、仕様変更でカラムが増えたり、予期せぬエラーメッセージが混ざったりします。少しでもフォーマットが崩れると、Fscanf はパニックや無限ループ、データのズレなどの致命的なバグを引き起こします。

3. 実務で主流となっている解析手法

  • 構造化データ（主流）： JSON、YAML、XMLなど。これらは encoding/json などを使って構造体（struct）に安全かつ正確にマッピングします。現代のログ出力やデータのやり取りは、これが圧倒的な主流です。
