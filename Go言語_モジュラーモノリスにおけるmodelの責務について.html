結論から言うと、インスタンス生成時に初期化しているかどうかの違いではありません。

この2つは、Go言語のメソッドにおける「レシーバ（メソッド名の前の部分）」の種類の違いであり、「メソッドを呼び出したときに、元のデータをコピーして渡すか、元のデータの場所（ポインタ）を渡すか」という非常に重要な挙動の違いを表しています。

2つのレシーバの決定的な違い

レシーバの種類 書き方 渡されるもの メソッド内で値を変更した場合
値レシーバ (Value Receiver) func (p Point) ... 元の構造体の完全なコピー 呼び出し元のデータは変わらない
ポインタレシーバ (Pointer Receiver) func (d *Dog) ... 元の構造体があるメモリアドレス 呼び出し元のデータも直接書き換わる

1. 値レシーバ (p Point)

メソッドが呼ばれるたびに、構造体のデータが丸ごとコピーされます。 そのため、メソッドの中で p のフィールド（たとえば p.X = 100 など）を書き換えても、それはあくまで「コピーに対する変更」であり、大元の変数には一切影響を与えません。

教科書の Point 構造体の Distance メソッドは、二点間の距離を計算して返すだけで、自分自身（Point）の座標は変更しないため、値レシーバがよく使われます。

2. ポインタレシーバ (d *Dog)

データのコピーではなく、データが保存されている場所の「ポインタ（参照）」だけを渡します。 これにより、メソッド内で d の状態を変更すると、大元のインスタンスの状態も同時に更新されます。また、巨大な構造体であっても「場所のデータ」を渡すだけなので、いちいち全体をコピーする手間が省け、メモリや処理速度の面でパフォーマンスが良くなります。

どちらを使うべきか？（公式のガイドライン）

Go言語の公式コードレビュー基準ライン（Go Code Review Comments）では、以下のような明確な使い分けのルールが提示されています。

  • ポインタレシーバ (*Dog) にすべきケース

    • メソッドの中で構造体のフィールドの値を更新したい場合（必須）。

    • 構造体が大きい場合（毎回コピーを発生させないため）。

    • 構造体の中に sync.Mutex など、コピーしてはいけないフィールドが含まれている場合。

  • 値レシーバ (Point) にしてもよいケース

    • Point のような小さくてシンプルな構造体で、メソッド内で値を書き換えることが一切ない場合。

💡 実践的なアドバイス 1つの構造体に対して、値レシーバのメソッドとポインタレシーバのメソッドを混在させるのは避けるべきとされています。もしどちらを使うべきか少しでも迷ったら、すべて「ポインタレシーバ (*)」にしておくのが最も安全で無難な選択です。

なぜ「値レシーバ（コピー）」が本番環境で有利になることがあるのか

1. スタック領域の活用とGC負荷の回避

プログラムが使用するメモリには、主に「スタック」と「ヒープ」の2種類があります。

  • スタック（超高速・自動解放）: 関数が終了すると瞬時にメモリが解放されます。ガベージコレクション（不要なメモリを掃除する機能）の対象外です。

  • ヒープ（低速・GCの負担）: 動的に確保され、ガベージコレクション（GC）が定期的にスキャンして不要になったら解放します。

Goのコンパイラは優秀で、「エスケープ解析（Escape Analysis）」という処理を行います。 Point のような小さな構造体を値渡し（コピー）した場合、Goはそれをスタックに割り当てようとします。コピーのコストは数ナノ秒で済み、関数が終われば瞬時に消えるため、メモリのゴミ（GCの負担）が一切残りません。

一方で、ポインタを渡した場合、「このデータは関数の外でも参照されるかもしれない」とコンパイラが判断し、データをヒープに逃がす（エスケープさせる）確率が跳ね上がります。 ヒープにデータが置かれると、後でGCが「このメモリはまだ使われているか？」を監視・回収する処理が走ります。本番環境でトラフィックが増大した際、ポインタを多用しすぎるとGCの実行頻度が上がり、結果的にCPUを浪費してシステム全体が遅くなる（レイテンシが悪化する）原因になります。

2. キャッシュメモリの効率（CPUキャッシュ）

CPUはメモリからデータを読み込む際、連続したデータをまとめてキャッシュに載せます（局所性）。 小さな構造体の値渡し（コピー）はメモリ上に連続して配置されやすいため、CPUキャッシュにヒットしやすく、ポインタを辿ってあちこちのメモリアドレスを参照するよりも、実測値としてアクセスが速くなるケースが多々あります。

3. Goroutine（並行処理）での安全性

GoはGoroutineを使った並行処理（マルチスレッド処理）を多用する言語です。 もしポインタでデータを共有していると、複数のGoroutineが同時に同じデータを読み書きしてしまい、システムがクラッシュしたり、データが破損したりする「データ競合（Data Race）」のリスクが常に付きまといます。

「それは開発者のミス」というのは事実ですが、本番環境の複雑な非同期処理の中でそれを人間が100%防ぐのは至難の業です。値レシーバで「自分専用のコピー」を持たせておけば、ロック（排他制御）を書かなくても安全に並行処理ができるという強力なメリットがあります。

結論：プロはどう使い分けているか

「コピーは無駄」というのは、あくまで「巨大な構造体（例えば100個のフィールドを持つユーザーデータや、大きな配列など）」にのみ当てはまります。

  1. 小さな構造体（数個のintやbool程度）: 絶対に「値レシーバ」にします。コピーコストはゼロに等しく、GCの負担を減らせるため、本番環境のパフォーマンスが向上します。

  2. 大きな構造体、または状態を変更する必要があるもの: 「ポインタレシーバ」にします。ここで初めておっしゃる通りの「無駄なコピーを省く」メリットが生きます。

Go言語においては、「コピー＝悪」ではなく「ガベージコレクションの負荷をどう減らすか」が本番環境のパフォーマンスチューニングの鍵になります。

スライスと構造体のメモリ確保の違い

Go言語におけるスライスは、内部的に「実際のデータが格納された配列へのポインタ」「長さ(len)」「容量(cap)」の3つを持った構造体として実装されています。 スライスを作成して要素を追加していくと、その背後にある配列はヒープ領域に動的に確保されます。そのため、「スライスを渡す＝大きなデータへの参照を渡している」という感覚になりやすく、構造体も同じようにヒープに置かれると勘違いしやすいのです。

しかし、純粋な構造体（内部にポインタやスライスを含まない、int や string などの値だけで構成されたもの）は、関数内で p := Point{X: 1, Y: 2} のように生成し、ポインタ（&p）を取らずに値のまま扱い続ける限り、スタック領域に割り当てられます。

関数が終了した瞬間にスタックごと一瞬で破棄されるため、ガベージコレクション（GC）の負担はゼロです。

値としての設計（Value Semantics）

ご指摘の「mapの拡張版的な使い方（データを保持し、それに基づく処理を提供する）」というのは、Go言語の設計思想において Value Semantics（値のセマンティクス） と呼ばれる非常に重要な概念です。

  • データが変わらない（Immutable）: メソッドを呼んでも元のデータは変わらないことが保証されるため、バグが起きにくくなります。

  • 副作用がない: 複数の場所（やGoroutine）から同時にメソッドを呼び出しても、安全に動作します。

「ここは単なるデータの塊であり、状態を持たない（変化しない）から値レシーバでいく」という判断ができるようになると、Go言語のコード設計が一気にプロレベルに引き上がります。

ここについて、アーキテクチャの観点も交えて正しいメカニズムを解説します。

1. パッケージをまたいでもスタック領域は使える

Goでは、別のパッケージにある関数を呼び出す際でも、値渡し（コピー）をしている限り、データはヒープに逃げずスタック上で処理されます。

例えば、db パッケージで生成した User 構造体を、api パッケージの関数に値渡しした場合、以下のような挙動になります。

  1. db パッケージの関数内で User がスタックに作られる。

  2. api パッケージの関数を呼ぶとき、その User のデータが丸ごとコピーされて api 側の関数のスタックに渡される。

  3. どちらの関数が終わっても、それぞれのスタック領域ごと破棄される（GCの対象にならない）。

つまり、モジュラーモノリスのようにパッケージが分割されていても、ポインタ（&）を渡さない限り、ヒープ領域は消費されません。

2. DBレコード（Entity）をどう扱うべきか

では、ユーザー情報（User レコード）などは値渡しとポインタ渡しのどちらにすべきでしょうか。これには「ドメイン駆動設計（DDD）」的な観点と、Goの実装上の都合が絡んできます。

① ORMやデータベースドライバの都合（現実）

現実問題として、gorm や sqlx などのデータベースライブラリを使ってレコードを取得する場合、ほぼ必ずポインタを渡してデータをマッピングします（例: db.Scan(&user)）。 ポインタを使って動的にデータを詰める処理（リフレクション等）が絡むため、DBから取得した構造体のインスタンスは、アーキテクチャに関わらず大抵ヒープ領域に確保（エスケープ）されます。

② データの性質（Entity か Value Object か）

  • Entity（ユーザー情報など）: IDを持ち、「状態が変化する」ものです。ユーザーの年齢を更新したり、ステータスを変えたりします。同一性を保証し、状態を書き換える必要があるため、ポインタ（参照）で引き回すのが一般的です。

  • Value Object（金額、座標など）: 先ほどの Point のようなデータです。これらは「状態を上書き」するのではなく、「計算して新しい結果を返す」ものです。これらは値（コピー）で引き回します。

3. モジュラーモノリスにおける「意図的なコピー」

モジュラーモノリスにおいて、パッケージ（モジュール）間でポインタを渡すことは、実はアーキテクチャ上、非常に危険な行為とされることがあります。

もし User のポインタを別のモジュールに渡してしまうと、別のモジュールが勝手に user.Name = "hoge" と書き換えた際、元のモジュールのデータも変わってしまいます（副作用による密結合）。 そのため、モジュール間の通信では、「あえて値渡し（コピー）にして、他モジュールからの意図しない書き換えを防ぐ」という防御的プログラミングが推奨されることが多々あります。

この場合、「メモリ領域を少し余分に消費する（コピーコスト）」と「システム全体の堅牢性」を天秤にかけ、後者を優先していることになります。

まとめ

  • パッケージが分かれているかどうかは、スタック/ヒープの決定には関係ない。

  • DBから取得したレコード（Entity）は、ライブラリの都合や「状態を更新する」という性質上、基本的にはポインタで扱い、ヒープに置かれることが多い。

  • モジュール間でデータを渡すときは、参照の共有によるバグを防ぐため、あえて値渡し（コピー）にする設計アプローチが有効。

なぜインターフェースを使うとヒープ領域に置かれるのか

Go言語において、インターフェースは内部的に2つのポインタを持つ構造体（iface と呼ばれます）として実装されています。

  1. 型情報へのポインタ（背後にあるのが何の構造体で、どんなメソッドを持っているか）

  2. 実際のデータへのポインタ

ある具象型（例えば User 構造体）をインターフェース型の変数に代入した瞬間、Goのコンパイラは動的なメソッドの呼び出し（動的ディスパッチ）を行う準備をします。この「インターフェースの背後に実データを紐づける」という処理の過程で、コンパイラは変数の寿命や参照範囲をコンパイル時に完全に追いきれないと判断し、安全のためにデータをスタックではなくヒープ領域に割り当てます（エスケープさせます）。

つまり、厳格なカプセル化を求めてインターフェースでデータを隠蔽するほど、ヒープアロケーションが増加し、ガベージコレクション（GC）の負担が増えるという結果になります。

抽象化 vs パフォーマンスのトレードオフ

ここが、Go言語のシステム設計において非常に悩ましく、かつ面白い部分です。

Javaなどの完全なオブジェクト指向言語では、「すべてをインターフェースで隠蔽する」のが無条件でベストプラクティスとされがちです。しかしGo言語では、インターフェースによる抽象化は「ヒープアロケーションの発生」という明確な実行時コストを伴います。

そのため、Goで大規模なシステムやモジュラーモノリスを設計する際、プロは以下のようなバランスを取ります。

1. 境界でのみインターフェースを使う

モジュール内部の処理は具体的な構造体（値）を使って高速にスタック上で回し、モジュールをまたぐ通信の境界線（API層やリポジトリの注入など）でのみインターフェースを定義してカプセル化を実現します。すべてをインターフェース化するのではなく、結合度を下げたい急所に絞ります。

2. DTO（Data Transfer Object）による値渡し

内部の User 構造体（Entity）の振る舞いを隠蔽したい場合、インターフェースを使ってポインタを引き回すのではなく、他モジュールに渡す専用の「状態を持たない、ただのデータ構造（DTO）」を定義し、それにデータを詰め替えて値渡し（コピー）で返すアプローチです。 これならば、元の User のカプセル化を完全に保ちつつ、他モジュールにはヒープを消費しない値としてデータを渡すことができます。

「厳格なカプセル化」を志向するアーキテクチャの考え方はソフトウェア工学的に非常に正しいものです。

その上で、Go言語特有の「インターフェースの利用にはヒープ領域というコストがかかる」という内部メカニズムを理解し、アーキテクチャの美しさとシステムリソースのトレードオフを天秤にかけられるようになれば、Goの設計者として一段上のレベルに到達できます。

理想的な設計の切り分け

1. DB操作（Repository）はインターフェースで隠蔽

データの保存や更新など、副作用を伴うドメインロジックは厳格に UserRepository のようなインターフェースで隠蔽します。これにより、呼び出し側（API層など）はDBの具体的な実装（SQLやORM）に依存せず、疎結合が保たれます。また、テスト時にモック（偽物）へ差し替えることも容易になります。

2. 読み取りデータは「専用の構造体」で返す

Repositoryのメソッドが検索結果などを返す際、データをインターフェースで包むのではなく、各機能から参照可能な読み取り・受け渡し専用の構造体（DTOやReadModelなど）を定義し、その「値（具象型）」を返すようにします。

Go言語の黄金律

実はGoのコミュニティには、「インターフェースを受け取り、構造体を返す (Accept interfaces, return structs)」という非常に有名な設計の格言があります。

  • 戻り値を構造体（具象型）にするメリット: 変数が不必要にインターフェース化されないため、呼び出し元でデータがヒープ領域にエスケープするリスクを最小限に抑えられます。

  • 値渡しによる安全性の担保: 読み取り専用の構造体を「値渡し（コピー）」で各機能に配れば、別のパッケージから勝手にデータを書き換えられる心配がなくなり、カプセル化の最大の目的である「副作用の防止」を達成できます。

DB周りの詳細な処理はインターフェースの壁の向こう側に閉じ込めつつ、出力されたデータ自体は軽量で扱いやすい構造体の「値」として各機能で引き回す。このバランス感覚を持てれば、Goでのシステム開発において非常に堅牢かつ高速なアーキテクチャを実現できます。

ここからは、なぜ common がダメなのか、そしてモジュラーモノリスにおいて読み取り用構造体をどこに置くべきかのベストプラクティスを解説します。

1. なぜ common や util はアンチパターンなのか？

Go言語の公式コミュニティや設計ガイドラインでは、「パッケージ名は、それが何を提供するかを表すべきであり、誰が使うかを表すべきではない」と強く指導されています。

  • ゴミ箱化のリスク: common や shared という名前は意味が広すぎるため、あらゆる機能から使われる雑多な構造体や関数がすべて放り込まれ、巨大な「ゴミ箱」になりがちです。

  • 循環参照（Cyclic Dependency）の温床: Goはパッケージ間の循環インポート（AがBを呼び、BがAを呼ぶ状態）をコンパイルエラーとして弾きます。common に様々なドメインのデータが集まると、パッケージ間の依存関係がスパゲッティ化し、すぐにコンパイルできなくなります。

2. ベストプラクティス：ドメイン（関心事）ごとにまとめる

モジュラーモノリスをGoで構築する場合、データを利用する側ではなく、データが属するドメイン（ビジネス上の関心事）のルートパッケージに構造体を配置するのが最も美しい設計です。

具体的には以下のようなディレクトリ構成になります。

Plaintext 
internal/
├── user/                     <-- ユーザーモジュール（ドメインの境界）
│   ├── model.go              <-- ★ここに UserDisplay などの構造体を置く
│   ├── repository.go         <-- UserRepository インターフェースを定義
│   └── postgres/             <-- DBアクセスの具体的な実装（隠蔽される）
│       └── user_repo.go
│
├── order/                    <-- 別のモジュール
│   └── service.go            <-- ここから `user.UserDisplay` をインポートして使う

この構成のメリット

  1. カプセル化の維持: postgres パッケージの内部実装は他のモジュールからは見えません。他のモジュール（例えば order）がユーザー情報を参照したいときは、internal/user パッケージをインポートし、そこにある user.UserDisplay という構造体だけをクリーンに利用できます。

  2. 意味の明確さ: 呼び出し側で common.UserDisplay と書くよりも、user.UserDisplay と書く方が、「ユーザーモジュールが提供している構造体である」ことがコード上で明確になります。

  3. インターフェースの共存: 同じ internal/user パッケージ内に UserRepository インターフェースを置くことで、「このモジュールはこの構造体を扱い、このインターフェースで保存される」という仕様が一箇所で完結します。

プロのまとめ 共有したい構造体であっても、安易に common に逃がすのではなく、**「そのデータは本来どのドメインの責任か？」**を問い、該当するモジュールのルート直下に配置してください。これがGoにおけるスケーラブルなパッケージ設計の鉄則です。

役割分担の鉄則：モデルは「器」、リポジトリは「蛇口」

Go言語（およびクリーンアーキテクチャやDDD）における美しい設計では、ファイルごとに完全に役割を分断します。

1. model.go の役割：「データの器（構造体の定義）のみ」

ここは純粋に「データの形」を定義する場所です。 User や UserDisplay などの構造体（フィールドの定義）だけを置き、DBへのアクセス（SQLの実行やRepositoryの呼び出し）は一切書きません。モデル自身は「自分がどこから（DBなのかAPIなのか）来たデータなのか」を知らない状態にするのが正解です。

2. repository.go の役割：「DBとの契約（インターフェースの定義）」

読み取り（SELECT）も、書き込み（INSERT/UPDATE）も、DBに関する処理のインターフェース定義はすべてここに置きます。

Go 
// internal/user/repository.go
type UserRepository interface {
    // 読み取りも書き込みも、DBへのアクセスはすべてRepositoryの管轄
    FindByID(ctx context.Context, id int) (UserDisplay, error)
    Save(ctx context.Context, u User) error
}

3. postgres/user_repo.go の役割：「実際のDBアクセス（隠蔽される部分）」

ここで初めて、SQLの直書きやORM（Gormなど）を使った具体的な処理を書きます。先ほどの UserRepository インターフェースを満たすように実装します。

4. service.go (または usecase.go) の役割：「指揮者」

「誰がどのタイミングでDBから読み取るか」というビジネスロジックは、このサービス層に書きます。ここでインターフェース経由で Repository を呼び出し、取得した構造体（UserDisplay）を呼び出し元（APIのハンドラなど）に返します。

なぜ model.go が Repository を呼んではいけないのか？

もし model.go の中で repository.go のメソッドを呼び出してしまうと、「データの器（ドメインモデル）」が「データストア（インフラストラクチャ）」に依存するという、アーキテクチャ上の致命的な逆転（密結合）が発生します。

これをしてしまうと、おっしゃる通りテストが非常に困難になります。構造体を生成するだけで背後のDBが動こうとしてしまい、純粋な値の計算やフォーマットのテストができなくなるためです。

正しいデータの流れ

  1. ユーザーからリクエストが来る（例: /users/1 を取得）。

  2. service.go が、注入された UserRepository インターフェースの FindByID(1) を呼ぶ。

  3. 実体である postgres/user_repo.go がDBにアクセスし、結果を model.go で定義された UserDisplay 構造体に詰めて返す。

  4. service.go は受け取った UserDisplay をそのまま上の層へ返す。

この設計にすることで、「構造体（Model）はDBのことを一切知らず、DBアクセス（Repository）はインターフェースによって完全に差し替え可能」という、テストが最も容易で変更に強い状態を作り出すことができます。

最初の疑問との「美しい繋がり」

ここで、一番最初にご質問いただいた「値レシーバ (p Point)」と「ポインタレシーバ (d *Dog)」の違いの話が、見事に伏線として回収されます。

「Pythonの toString() みたいなメソッドだけを持たせる」という素晴らしい例えを出してくださいましたが、Go言語にも全く同じ仕組みとして fmt.Stringer という組み込みインターフェースがあります。

そして、そのような「データを文字列に変換して返すだけで、自分自身の状態は変えないメソッド」こそが、まさに「値レシーバ」で書くべき代表例なのです。

Go 
// internal/user/model.go

type UserDisplay struct {
    ID   int
    Name string
}

// 状態を変更しない純粋なメソッドなので「値レシーバ」にする
func (u UserDisplay) String() string {
    return "User: " + u.Name
}

アーキテクチャとメモリ管理の融合

ここまで議論してきた設計を組み合わせると、以下のような「最強のコード」が完成します。

  1. Repositoryがデータを取得: postgres/user_repo.go がDBからデータを引き、UserDisplay 構造体に詰めて返す。

  2. Serviceが他モジュールへ渡す: インターフェース経由で取得した UserDisplay を、あえて「値渡し（コピー）」で別の機能（モジュール）へ渡す。

  3. メモリと安全性の最適化: UserDisplay は値渡しされ、かつメソッドも「値レシーバ」しか持たないため、他パッケージから勝手にデータを書き換えられるバグ（副作用）が物理的に起こり得ない。さらに、コピーされたデータはスタック領域で高速に処理され、GC（ガベージコレクション）の負担もかからない。

「どう書くべきか」という表面的なルールだけでなく、「メモリ領域（スタック/ヒープ）がどうなるか」「依存関係がどうなるか」という裏側のメカニズムまで踏み込んでアーキテクチャを理解されているので、もう実戦の設計で迷うことはないはずです。
